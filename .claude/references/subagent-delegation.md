# サブエージェント委任設計

## 基本方針

サブエージェントを利用できる環境では、親エージェントは詳細ドキュメント生成や調査をできるだけ委任する。

親エージェントの責務:

- ユーザーとの対話
- 最初のヒアリング
- 提案内容の最終設計
- サブエージェントへの作業分割
- 成果物の統合
- ファイル間の整合性確認
- CLI セットアップ実行判断
- 最終報告

サブエージェントの責務:

- 担当範囲の詳細仕様作成
- 画面仕様作成
- DB設計の下書き
- 開発フェーズ詳細の下書き
- ユーザータスクの洗い出し
- アナリティクス設計
- 技術選定に関する補助調査

## 委任してよい作業

以下は積極的にサブエージェントへ委任する。


| 委任ID  | 担当領域    | 主な出力先                                     | 内容                                |
| ----- | ------- | ----------------------------------------- | --------------------------------- |
| D-001 | 画面仕様    | `docs/screens/`                           | 画面一覧、各画面の目的、UI要素、状態、バリデーション、遷移    |
| D-002 | 機能仕様    | `docs/functional-requirements/`           | 機能ごとの仕様、API、バリデーション、関連画面          |
| D-003 | DB設計    | `docs/database/`                          | テーブル、リレーション、RLS、インデックス、業務制約       |
| D-004 | 開発フェーズ  | `docs/development-phases/`                | 実装順序、依存関係、完了条件、参照すべき機能仕様          |
| D-005 | ユーザータスク | `docs/user-tasks/`                        | APIキー取得、外部サービス作成、Webhook設定、ログイン作業 |
| D-006 | 環境変数    | `docs/env-variables.md`                   | 必要なキー、用途、取得元、設定タイミング              |
| D-007 | アナリティクス | `docs/functional-requirements/analytics/` | GA4/GTMイベント、カスタムディメンション、設定スクリプト   |
| D-008 | 技術補助調査  | 親エージェントへ報告                                | 技術選定の確認、ライブラリ候補、注意点               |


## 委任しない作業

以下は親エージェントが担当する。

- ユーザーへのヒアリング
- ユーザー承認前の最終提案
- CLI セットアップ実行
- Git 操作
- `.env.local` の作成や更新
- 生成物全体の最終統合
- サブエージェント成果物の採否判断
- ユーザーへの最終報告

## 委任タイミング

### 提案前

原則として、提案前はサブエージェントを使わない。ユーザーに最初の概要だけを聞き、親エージェントが一括提案を作る。

ただし、ユーザーが明示的に「調査して」「サブエージェントに分担して」などと依頼した場合は、技術補助調査のみ委任してよい。

### 提案承認後

提案が承認されたら、ドキュメント生成を並行委任する。

推奨分割:

1. 画面仕様エージェント: `docs/screens/`
2. 機能仕様エージェント: `docs/functional-requirements/`
3. DB設計エージェント: `docs/database/`
4. フェーズ設計エージェント: `docs/development-phases/`
5. ユーザータスク・環境変数エージェント: `docs/user-tasks/` と `docs/env-variables.md`
6. アナリティクスエージェント: docs/analytics/

## 委任プロンプト共通テンプレート

サブエージェントには、以下の情報を必ず渡す。

```markdown
あなたは開発プロジェクト初期構成ジェネレーターのサブエージェントです。

## 承認済み提案
{ユーザーが承認した提案内容}

## 担当範囲
{担当するディレクトリまたはファイル}

## 出力ルール
- すべて日本語で記述する
- ファイル名は kebab-case にする
- 環境変数の実値を書かない
- 不明点は `<!-- TODO: 要確認 -->` コメントで残す
- 担当範囲外のファイルは編集しない
- 他のサブエージェントも並行作業している前提で、共通IDやファイル名を勝手に変更しない

## 最終報告
- 作成・更新したファイル一覧
- 判断に迷った点
- 親エージェントが統合時に確認すべき点
```

## 担当別プロンプト補足

### D-001 画面仕様

- `docs/screens/screens-summary.md` を作成する
- 各画面ディレクトリに `spec.md` を作成する
- `screen.png` 生成に必要な画像生成プロンプト案も `spec.md` に含める
- 画面IDは `U-001`、`A-001` のように本文で管理する

### D-002 機能仕様

- 画面仕様と提案内容から機能単位に分割する
- APIエンドポイント、バリデーション、関連テーブルを記述する
- 仕様の詳細は機能仕様に寄せ、フェーズ文書には重複させない

### D-003 DB設計

- テーブル一覧、主要カラム、リレーション、RLSを設計する
- Mermaid ER図を含める
- テーブル10以上の場合は `overview.md`、`tables.md`、`rls-policies.md`、`migrations.md`、`seed-data.md` に分割する

### D-004 開発フェーズ

- フェーズごとの目標、手順、完了条件を書く
- 機能仕様ファイルを参照し、同じ仕様を二重管理しない
- 前提ユーザータスクがある場合は冒頭に明記する

### D-005 ユーザータスク

- エージェントが実行できない作業だけを抽出する
- どのフェーズの前に必要かを明記する
- 完了確認方法を書く

### D-006 環境変数

- `.env.local` に必要なキーを一覧化する
- 用途、取得元、必須/任意、利用フェーズを記述する
- 値はプレースホルダーのみ使う

### D-007 アナリティクス

- GA4イベント名、パラメータ、カスタムディメンションを設計する
- GTMを使う場合はタグ・トリガー・変数の構成を記述する
- 設定補助スクリプトが必要な場合は `scripts/` 配下に作成する

## 統合チェックリスト

親エージェントはサブエージェントの作業後、以下を確認する。

- 参照パスが存在する
- 画面IDが重複していない
- 機能IDが重複していない
- フェーズ番号が連続している
- ユーザータスクとフェーズ前提が対応している
- DBテーブル名と機能仕様の関連テーブルが一致している
- `.env.local` に必要なキーと `docs/env-variables.md` が一致している
- 実際のAPIキーやシークレットが書かれていない
- 担当範囲外の変更が混ざっていない
- 生成先プロジェクトの `.codex/AGENTS.md` と `.claude/CLAUDE.md` が整合している
